# Redemption claim recording (local only)

Migration 005 and RedemptionClaims implement a trusted internal evidence recorder, not a redemption executor. No public API, runtime role grant, reserve reservation, token lock/burn, payment, fee allocation or ledger posting is added.

## Lifecycle
Immutable requests freeze owner, ORIO token asset/units, payout asset/units, recipient, election and approved quote digest/expiry. Both amounts must be positive canonical integer strings (up to 78 digits). The caller supplies independently approved economics; this module does not calculate fees, appreciation, bootstrap, rounding or residuals.

Append-only versioned evidence derives REQUESTED → CLAIM_VERIFIED → SETTLEMENT_PENDING → SETTLED. CLAIM_VERIFIED records a trusted adapter assertion of the exact claim and unique claim reference; it does not itself lock tokens or prove ownership. SETTLEMENT_PREPARED checks the frozen approved payout, active matching master election and quote expiry after holding request/election locks. It is not permission to dispatch funds. EXECUTION_UNCERTAIN moves a pending request to REVIEW_REQUIRED, preserving the exact obligation without automatic retry, cancellation, refund or invented recovery policy.

SETTLED means the recorder accepted authenticated historical evidence of BOTH the exact burn and exact payout. This code did not perform either action or post financial accounting. Historical completion may be recorded from pending/review even after the election pauses or changes, but must match the frozen request's election, owner, asset, amounts and recipient. Partial or mismatched evidence cannot mark settled. Authenticity/finality must be verified independently before calling the recorder; a digest is only an identifier, not proof.

## Atomicity and idempotency
A request row lock serializes competing events. Expected version fences stale attempts. Identical event retries return the original historical receipt; conflicting event IDs or request reuse fail. Immutable requests/evidence/receipt records reject update/delete/truncate. Burn and payout references are distinct and unique in the redemption registry, including across roles and requests. Failure on a second reference rolls back the first reference and event together. These are NOT cross-module or cross-chain replay guarantees: adapters must canonicalize chain/transaction/event identity and a future shared settlement registry must coordinate conversion, redemption and ledger consumption. Privileged database owners remain able to bypass controls and require separate administration/audit controls.

## Remaining acceptance
Authenticated ownership/encumbrance and finalized-chain adapters, independently approved monetary policy, reserve and compliance checks, bounded scoped writer identity, economic authorization, a real atomic accounting/outbox integration, burn/payout orchestration with external idempotency, release gates at actual dispatch, partial-execution recovery, cancellation and governed compensation are still required. Do not wire this recorder to real money or infer production readiness from local tests. No financial release or route is activated.

005 is local-only and has NOT been applied to AWS. Existing migrations were preserved. Tests use an isolated loopback PostgreSQL database and synthetic master metadata, while applying the actual new SQL with only helper/master-schema names substituted. Verification on 2026-11-12: strict TypeScript passed and the full isolated suite passed 81/81 tests, exit 0. Coverage includes immutable input and evidence, exact quantities, repeated/conflicting requests/events, concurrent claims, duplicate/cross-role receipts, atomic rollback on mismatched/partial receipts, uncertain execution, historical completion after pause, and expiry after election-lock waits.
