## Ordered importer worker

SQL023 and the private Node 24 entry point prepare hosted qualification on a separate Base Sepolia database. The migration requires the database name `orio_control_qualification` and creates an inert permission group. An administrator must separately initialize the verified deployment and bind a dedicated IAM login. Row and column permissions restrict reads and state updates to that deployment. Narrow database functions derive permitted account identities, check receipt ownership and confine postings to the bound deployment. The group has no direct access to shared receipt or ledger tables and cannot enroll another deployment.

The importer remains trusted to verify receipts and execute the approved transition before it uses its database authority. Its login can change its bound cursor and claim Base Sepolia receipt references, so keep the database isolated from other importers and all production accounting. The role and runtime intentionally cannot be used with the original database or with mainnet. The private handler accepts only `{"action":"step"}`, verifies the pinned RDS trust bundle, connects with a short-lived IAM token, and uses deployment-configured read-only providers. Use a single concurrent invocation and an alarm on repeated rejection when wiring scheduling. Distinct hostnames are a configuration check. Verify actual provider independence separately.

The build command from `services/control-foundation` is `node scripts/build-valuation-journal-lambda.mjs <output.zip> --autonomous-import`. The ZIP build checks compilation and rejects an invalid invocation with no live connection. Integration tests exercise the restricted login, two-deployment isolation, forbidden shared-table access, purchase and payout accounting, and rollback of a split journal. Hosted qualification still needs an isolated database, authenticated IAM binding, verified contract/provider identities, restricted egress, invocation permissions and a live Base Sepolia run.

The proposed [AWS foundation](../../infrastructure/aws/autonomous-import-qualification-foundation.json) defines a new VPC with private compute and isolated data subnets, an encrypted disposable PostgreSQL 17 database, TLS enforcement and IAM database authentication. It uses a single NAT gateway for testnet HTTPS and leaves the database without an internet route. It needs AWS-native template validation and inspection of the change set in account 720232346199 before use.

Once the autonomous contract manifest is verified on Base Sepolia, run `node scripts/bootstrap-autonomous-qualification.ts <instance-id> <physical-db-resource-id> <verified-deployment-json> <pinned-rds-ca>` in a private maintenance session. The command checks the account, physical database identity and RDS protections before retrieving the disposable database's managed credential in memory. It atomically installs the fresh schema and binds the passwordless worker. It rejects an occupied schema or role and reports an ambiguous commit as requiring inspection. The template does not provision the Lambda, its execution role, provider credentials or scheduling. Bind the Lambda role to the exact returned physical DB resource ID and dedicated worker login in the next deployment step.

`AutonomousImportWorker` connects bounded two-source finalized event discovery to `AutonomousSettlement`. Each private step reads the durable deployment cursor, checks both chain identities, uses the lower finalized head, and scans at most 2,000 blocks and 10,000 events. It compares normalized ordered events and canonical end-block anchors across both sources, rechecking anchors after discovery. Removed/duplicate/out-of-filter events, disagreements and invalid cursors fail before accounting.

The first required event selects the next action. Ordinary token transfers import before later checkpoints; mint/burn events select their next same-transaction monetary checkpoint; claims retain their fixed-recipient settlement proof. An empty agreed interval advances only through the settlement target's independent empty-coverage verification. Every target action rechecks finalized receipt ownership, event coverage and monetary accounting inside its existing atomic/idempotent path. Discovery is not an authorization substitute or a third-party cryptographic proof of log completeness. A compromised pair of configured sources remains a trust-model risk.

The worker neither signs nor sends transactions, creates permissions, reads credentials, initializes deployments or accepts customer-controlled endpoints. Concurrent/restarted runs may attempt the same fact; durable target idempotency prevents duplicate booking. Accounting failures propagate and do not advance a separate discovery cursor. Deployments must provide a trusted target bound to the same admitted configuration, protect invocation, and limit database access. No hosted runtime grants were added by this source change.

A full 64-request redemption epoch can exceed the ledger's 128-posting limit, even though the contract admits and settles it. The importer groups postings by asset when the combined journal exceeds that limit. The fact links to the primary journal under the original receipt reference. Companion journals use the same reference with a numbered `/part:` suffix, ordered by asset. All journals, receipt ownership, payout and reserve reconciliation, the fact and the cursor commit in one transaction. The full-capacity integration fixture uses distinct owners and recipients and proves that a failure on the second journal leaves neither the first journal nor its receipt claim committed.

Seven focused tests cover ordering, mint/burn grouping, claim selection, source disagreement, duplicate/removed logs, wrong chains, range limits, lower finality, anchor drift, orphan burns and target failures. Actual disconnected contract/PostgreSQL integration now uses the worker for purchase, transfer, payout, full redemption, reopening and company-fee reconciliation; injected journal failure proves rollback. Strict typechecking and 281 local checks pass. This does not establish live provider admission, production financial readiness or mainnet support; hosted scoped importer permissions/deployment and monitored scheduling remain outstanding.

## Customer authorization and execution

`contracts/sdk/autonomous-wallet.mjs` builds purchase approvals/calls, EIP-712 withdrawal consent, admission, whole-epoch settlement, fixed-recipient payout claims, cancellation/expiry release and zero-protocol-fee transfers. All amounts/nonces/times use canonical integer strings. Chain, contract, epoch, recipient, amount and minimum payout are bound to customer consent. Builders reject mainnet and do not sign, send or choose credentials. They accept trusted deployment/snapshot inputs; deployment admission and live freshness checks belong to the caller.

Redemption has three separately executable phases: admission, settlement and payout delivery. The wallet must distinguish tokens locked, payout funded and payout delivered. Each phase needs its own complete network-cost authorization; a quote for admission is not authorization to charge for later settlement/claim. A customer may receive several claims at the same recipient; the claim contract delivers their aggregate. The module is an application connection layer, not a completed hosted consumer authentication/passkey interface.

The actual EntryPoint/account/paymaster tests execute purchase, ERC-1271 withdrawal admission, settlement, claim and transfer while the account has zero ETH. The database integration reserves prepaid user gas before protected permit signing, checks actual EntryPoint debit, separately charges user gas, refunds unused estimates and prevents duplicate closure. Reserve/claim cash and gas balances use distinct accounts/assets. Local synthetic funding, KMS protocol emulation, block anchors and zero L1 charges are explicitly not live AWS, Base finality, gas-conversion pricing or L1/bundler allocation evidence.

The company paymaster can withhold its own service. A separate test disables it and relays a smart-account owner's signed withdrawal through an unrelated native-gas caller; the controller accepts that request without company approval. This does not fund an alternative relayer or complete its user-gas billing. Current qualification accounts pin their paymaster for account execution; public admission/settlement/claim are the protocol fallback. Do not describe the gas service as unconditionally available.

## Finalized accounting

The controller emits explicit start/checkpoint boundaries for purchases, paid or empty epochs, zero-supply reconciliation and company distributions. Withdrawal allocation events identify owner and recipient. `finalized-autonomous.ts` requires two configured readers, canonical finalized receipts, exact event encoding and corresponding token mint/burn/custody movements. Claim funding must match both aggregate vault-to-claims cash and each recipient credit; actual payment requires a separate claims-to-recipient transfer and claim event. Extra or substituted movements fail verification.

`AutonomousSettlement` independently recomputes purchase/redemption economics with the approved monetary engine, including rounding and zero-supply reopening. Checkpoints must exactly match supply, price, reserve, company fees and funded pending claims. Database row locks serialize imports. All event ownership, accounts, journals, immutable facts, state/version and chain-log cursor updates commit together. Identical retries return the original receipt; conflicting/reused/out-of-order evidence fails. Mint/burn events cannot enter as ordinary wallet transfers. Errors leave prior state intact. No customer records or credentials enter reports.

Before advancing, the importer compares complete required-event ranges from both configured readers, starting at the pinned deployment block. A skipped ordinary token transfer, monetary checkpoint or payout claim stops the later import before its cursor moves. The integration regression omits a real transfer, rejects the later redemption, imports the missing transfer and then succeeds. Bounded empty-history catch-up appends finalized range evidence without posting a financial journal. Queries span at most 2,000 blocks each and 10,000 blocks/events per progression. Long outages require repeated verified catch-up; they cannot reset history. This completeness guarantee depends on the admitted independent RPC trust model, not cryptographic receipt-root proofs.

Funded claims are segregated cash/liabilities, not current reserve backing. Zero-supply reconciliation may reopen with prior funded claims outstanding because their cash has already left backing and remains entirely owed to recipients. Unfunded obligations cannot be passed off as funded claims. Rounding remains in separate USD54 memo accounts. Company distributions debit only recorded company cash. Missing claim deliveries, wallet transfers or company distributions stop reconciliation instead of concealing the difference.

`pending-migrations/022_autonomous_settlement.sql` creates owner-only tables with append-only facts; it grants no runtime or public permissions. Existing SQL and monetary importers remain unchanged. The migration is tested in isolated temporary PostgreSQL databases, passed the hosted clone rehearsal and was applied to the original database on November 21. A restricted hosted importer service remains required; schema installation alone grants no application authority.
